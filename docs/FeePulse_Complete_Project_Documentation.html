1. Project Introduction

FeePulse is a dedicated financial copilot built specifically for independent tutors, home educators, and micro-coaching academies in India.

Independent tutors operate a high-trust, relationship-driven business. While generic accounting software (such as Tally, QuickBooks, or Zoho Books) caters to GST supply chains, inventory management, and corporate double-entry ledgers, independent tutors face an entirely different everyday operational struggle:

  • Tutors juggle fee notes across physical notebooks, WhatsApp chats, and fragmented spreadsheets.
  • Parents pay irregularly in unpredictable partial installments (e.g., ₹1,500 now, ₹1,000 two weeks later, ₹500 in cash).
  • WhatsApp payment commitments ("Sir, will pay next Tuesday") are easily forgotten, quietly slipping into uncollected bad debt.
  • Meanwhile, fixed operating overheads (classroom rent, teacher honorariums, electricity) arrive on strict calendar deadlines.
  • Tutors only realize a cash deficit after they are already short on rent day.

FeePulse solves this by unifying fee tracking, installment accounting, WhatsApp promise tracking, and predictive 30/60/90-day cashflow runway into a single automated back-office workspace.

4. Quick 5-Step Demo Workflow

  1. Open Financial Dashboard (/): View the live financial cockpit, outstanding balances, overdue fee aging, and active priority queue.
  2. Add a Student (/customers): Navigate to Customers, click Add Student, and enroll a new student with monthly tuition fee details.
  3. Issue a Fee Invoice (/invoices): Go to Invoices, click Create Invoice, select the student, add tuition items, and set the due date.
  4. Record a Partial Payment (/payments): Go to Payments, click Record Payment, choose the invoice, enter a partial amount (e.g. ₹3,000 on a ₹7,500 invoice), and notice the remaining balance update automatically.
  5. Inspect Cashflow & Recovery Queue: Open Cashflow to inspect the updated daily inflow schedule, then open Recovery Queue to see the remaining balance prioritized for follow-up.

6. Architecture & Financial Security Safeguards

  • ACID Row-Level Mutex Locking: Concurrent payments on the same invoice are serialized at the PostgreSQL database layer via SELECT ... FOR UPDATE row locks, preventing negative balances and race conditions under simultaneous submissions.
  • Integer Paise Financial Precision: All monetary calculations convert rupees into integer paise (Math.round(amount * 100)) during computation, eliminating JavaScript floating-point errors (such as 0.1 + 0.2 !== 0.3).
  • Durable Payment Idempotency: Payments are bound to unique request idempotency keys and external UTR / Cheque references (uk_payments_business_reference), rejecting duplicate submissions at both the API and database constraint layer.
  • Strict Multi-Tenant RLS Isolation: All database tables enforce PostgreSQL Row-Level Security scoped to the authenticated user's business_id. Cross-tenant data leakage is prevented at the database kernel.
  • Human-in-the-Loop AI Control: AI endpoints never alter financial ledgers autonomously. Extracted amounts, dates, and reminder drafts require explicit tutor approval before persisting.
  • Streaming-Safe Request Limits: AI and API endpoints enforce bounded body size limits (< 8MB) and sliding-window rate limiting (30 req/min) to prevent resource exhaustion.
